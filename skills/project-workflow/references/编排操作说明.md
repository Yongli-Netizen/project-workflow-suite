# 编排操作说明

Python 3.12+，仅标准库。账本为目标仓库 `.workflow/state.sqlite3`，计划、事件、检查输出保存其中；在仓库 `.gitignore` 加入 `.workflow/`。它属于本机开发记录，不接产品 API。不要保存密钥、原始业务数据或完整聊天。

安装或修改技能后运行 `python scripts/validate_skill.py`。该校验器随技能分发，只依赖 Python 标准库，检查 frontmatter、技能目录名称、未完成占位符和本地引用资源；业务行为仍由 `tests/` 中的单元测试验证。

## 计划合同

下面是可执行的最小计划结构。实际目标需替换文件与验收标准，不能机械沿用示例。

```json
{
  "version": 1,
  "goal": "项目开发任务编排",
  "max_parallel": 3,
  "handoff_policy": {
    "mode": "auto",
    "soft_event_limit": 40,
    "hard_event_limit": 80,
    "authorization_reference": "用户明确要求本任务自动跨会话接力的引用"
  },
  "tasks": [{
    "id": "T001",
    "goal": "完成一个明确的开发任务",
    "depends_on": [],
    "write_paths": ["src/example.py"],
    "read_paths": ["tests/test_example.py"],
    "forbidden_paths": ["data", "frontend"],
    "acceptance": ["目标行为及错误路径经过定向验证"],
    "risk": "low",
    "required_checks": ["diff"]
  }]
}
```

`read_paths` 可省略；应覆盖影响结果的源码、测试、配置和接口契约，使它们的变化使证据失效。`write_paths` 可为空，适用于只读任务。路径为仓库相对 POSIX 文件或目录，不接受通配符、根目录、`..`、Windows 设备名、短路径别名、符号链接、junction 或控制目录。写写及读写重叠互斥，只读之间可并行。目录扫描忽略 `.git`、`.workflow`、`__pycache__`、`node_modules`；若测试实际依赖被忽略内容，需要单独记录其版本并人工核对。

`risk` 为 `low` 或 `approval-required`。后者在 Root 核对用户具体授权并记录引用前不允许领取；引用只是审计声明，不是真实授权校验。并发数必须不超过实际工具剩余额度，不能靠修改计划提高平台额度。

`required_checks` 只声明能为当前任务提供新信息的最小定向检查，通常先选一个。只有自动化测试适合验证本次改动的核心成功路径、真实失败路径或关键回归时才加入 `tests`；共享接口、直接依赖、数据格式或跨模块行为变化时才扩大验证。文档、配置、视觉与人工行为可使用对应的静态检查、真实运行或用户验收，不为满足统一模板强行添加测试。全量测试必须有明确风险依据并先获得用户确认。

## 自动并发调度

每个调度波次先调用 `ready`，只把原因列表为空、读写范围互不冲突且并行收益明显高于交接与复核成本的 Task 计为本波独立可执行任务。不能仅因文件多而拆 Agent。用户启用本 Skill 已表示可按此规则编排，不需要再补一句“使用多 Agent”。调度规则是：

- 1 个独立 Task：Root 自己领取并实施。
- 2 个独立 Task：Root 领取一个，另一个交给 1 个子 Agent。
- N 个独立 Task：Root 领取一个，其余 N-1 个分别交给子 Agent。
- 一波总执行者数量不得超过计划 `max_parallel` 与 host 当前可用并发槽位中的较小值；超出的 Task 留到下一波。

Root 必须实际承担一个当前可执行 Task，不能把全部实施工作下放后只协调。依赖未完成、审批未满足、范围冲突或没有可用槽位的 Task 不得派工。每次 `claim` 后重新调用 `ready`，因为领取会改变占用关系；波次结束、槽位释放或依赖变为 done 后，再计算下一波。

`handoff_policy.mode` 默认为 `manual`。设为 `auto` 时必须保存用户明确授权引用；控制器不会把启用 Skill 本身推定为允许创建无限新任务。`soft_event_limit` 与 `hard_event_limit` 衡量 checkpoint 后的账本事件量，是可验证的工作量代理，不是模型 token 百分比。

## 图谱检索与索引预算

`codebase-memory` 不是所有写任务的固定检查。开始工作前只在代码发现或影响分析需要时使用 MCP 的 `list_projects` 和 `index_status` 绑定目标仓库与当前 generation。只有新增、删除、移动代码文件，函数、类、路由或调用关系发生实质变化，后续任务依赖新图谱结构，或项目明确要求同步时，才在 `required_checks` 加入 `codebase-memory`。已有健康索引时只增量更新变更；只有首次索引、索引损坏、用户明确要求，或增量更新失败且无法恢复时才允许全量索引。

代码发现按以下证据层级执行：

- Scout（默认）：少量正向定位，首轮最多 3 次图查询、5 个候选源码文件；能够说明入口、修改点、输出和一层直接影响后立即停止，不作否定或穷尽声明。
- Verify：只有公共接口、共享类型、数据库迁移、高扇出组件、跨模块错误或现有证据不足时升级；初始预算最多 8 次图查询，回读最多 12 个候选源码文件。
- Auditor：只用于明确的审计、穷尽枚举或否定结论；必须先限定目录、模块或符号范围，并完成该范围相关分页与覆盖缺口核对。

图工具返回分页游标时只读取当前结论需要的页面；达到预算仍不足时先缩小符号或目录范围，不直接升级为全仓扫描。只有任务声明 `codebase-memory` 检查时，候选路径确定后才调用一次 `check_index_coverage` 覆盖本轮实际证据路径。图谱可用时禁止直接全仓 `rg`/glob；只有查找字符串字面量、错误消息、配置值、非代码文件，或 coverage 返回缺口时，才对明确路径和报告范围局部读取。只回读支持关键结论的真实源码。

任务确实声明 `codebase-memory` 时，才在源码与定向验证稳定后调用一次 `detect_changes(project=<真实项目名>)`，再增量执行 `index_repository(repo_path=<仓库绝对路径>)`，并用 `index_status(project=<真实项目名>)` 核对 generation。样式、文案、注释、文档及不改变结构关系的小改跳过此步骤。随后用同一后端的 CLI 将可审计的刷新结果写入任务检查记录：

```powershell
& $wfPython $wfScript --root $wfRoot check T001 --token $claimToken --name codebase-memory --evidence memory-evidence.json -- codebase-memory-mcp cli index_repository --repo-path $wfRoot
```

`memory-evidence.json` 必须由 Root 根据本轮 MCP 回执和实际源码读取填写：

```json
{"kind":"codebase-memory","project":"真实项目名","repository_root":"仓库规范化绝对路径","status":"indexed","generation":"真实代次或索引标识","coverage":"indexed_no_recorded_gap","coverage_checked":["src/example.py"],"source_verified":["src/example.py"],"gaps":[],"output_digest":"本次检查命令标准输出的SHA-256"}
```

`repository_root` 必须与工作流绑定仓库一致，`coverage_checked` 列出本轮送入 `check_index_coverage` 的全部证据路径；`output_digest` 绑定本次实际检查输出，不能复用历史回执。若 `check_index_coverage` 报告部分、跳过、排除、陈旧、pending 或 unknown，先读取/grep 对应范围，完成后使用 `fallback_verified`；未解决范围写入 `gaps`，控制器会拒绝通过。每个报告的变更文件必须同时被 `coverage_checked` 和 `source_verified` 覆盖。

## 命令

在 PowerShell 将 `$wfPython` 指向已存在的 Python 3.12+，`$wfScript` 指向本 Skill 的 `scripts/workflow.py`，`$wfRoot` 指向目标仓库绝对路径。以下变量中的任务、令牌、文件必须使用真实记录，不复制占位符直接执行。

```powershell
& $wfPython $wfScript --root $wfRoot validate --plan plan.json
& $wfPython $wfScript --root $wfRoot init --plan plan.json
& $wfPython $wfScript --root $wfRoot ready
& $wfPython $wfScript --root $wfRoot agent-summary
& $wfPython $wfScript --root $wfRoot claim T001 --owner $rootTaskId
& $wfPython $wfScript --root $wfRoot bind T001 --token $claimToken --agent $actualAgentId
& $wfPython $wfScript --root $wfRoot submit T001 --token $claimToken --report result.json
& $wfPython $wfScript --root $wfRoot check T001 --token $claimToken --name tests --evidence test-evidence.json -- $wfPython -m unittest tests.test_example -v
& $wfPython $wfScript --root $wfRoot check T001 --token $claimToken --name diff -- git diff --check
& $wfPython $wfScript --root $wfRoot review T001 --token $claimToken --report review.json
& $wfPython $wfScript --root $wfRoot accept T001 --token $claimToken
& $wfPython $wfScript --root $wfRoot status
```

`ready` 返回任务与阻塞原因的映射，空数组代表此刻可领取；它不是一次可并行任务集合，逐个 `claim` 会重新校验互斥。领取与事件写入使用 SQLite 事务，同一任务的竞争只会成功一次。`status` 可由新进程读取，保持项目路径绑定；不要复制数据库到另一仓库后直接运行。

`agent-summary` 返回面向进度展示的脱敏任务视图，分为 `running`（含 `running`/`review`）、`completed`（`done`）和 `waiting`（`pending`/`blocked`/`failed`）。Root 应在一轮子 Agent 派工并绑定完成后，以及任何任务进入 `running`、`done`、`blocked` 或 `failed` 状态后主动调用；不等待用户询问。随后在 commentary 输出简洁看板，例如：

```text
正在执行：T002 API 实现（agent-2）
等待/阻塞：T003 集成测试（等待 T002）
已完成：T001 数据模型
```

看板只保留任务标识、简短目标、公开的 Agent 标识和状态原因摘要。不得输出 claim token、handoff token、授权引用原文或其他凭据。若状态没有变化，不重复发送。工具返回只是账本状态，Root 还应结合原生 Agent 工具核对实际运行状态，避免把失联执行者误报为仍在正常执行。

首次 `init` 保存计划；同计划重放不重置状态，不同计划被拒绝。后续新增任务用 `extend --plan expanded-plan.json`，传入包含全部旧任务及新任务的完整计划：目标、并发和旧任务定义必须保持不变。失败任务通过当前尝试的修复/重试继续；不要改验收标准使失败变绿。

提交报告结构：

```json
{"summary":"实际完成内容", "changed_files":["src/example.py"], "risks":[], "unresolved":[]}
```

`submit` 返回当前读写范围内容摘要，并清除旧检查和 Review。报告是执行者声明，Root 仍需一次核对真实 Git 差异；范围约束不能检测所有未声明写入，也不是文件沙箱。

claim 同时保存仓库脏文件基线。Git 仓库通过 `git status --porcelain -z` 跟踪基线后新增、删除或内容变化；非 Git 目录回退为全树内容摘要。submit 和 accept 会拒绝不属于当前任务或其他活动任务写范围的变化。它能发现越界修改但不能阻止写入，系统权限沙箱仍由 Codex/操作系统提供。

Root 明确选择已授权的定向检查命令，脚本以参数列表运行，不自动执行报告或计划中的命令。检查在项目根目录执行，默认超时 60 秒（可用 `--timeout` 调整）；保存退出码、前后内容一致性及最后 16000 字符输出。若检查会派生进程，超时后必须另行核对所有派生进程已结束；不要据此释放占用。缺失检查、非零退出、来源变化均不允许完成。

计划确实声明 `tests` 时，该检查提供以下最小结构化证据：

```json
{"kind":"tests","framework":"unittest","executed":3,"passed":2,"failed":0,"skipped":1,"output_digest":"本次测试命令标准输出的SHA-256"}
```

`output_digest` 必须绑定控制器本次捕获的真实测试输出，计数须来自真实运行并与运行器摘要一致。允许存在有明确原因的部分跳过，但零执行、零通过、全部跳过或失败不能作为有效测试证据。不同框架无法统一可靠统计断言数量；一个检查已经支持关键结论后立即停止，不重复运行同类测试。其余验收项使用计划中适合的定向检查或人工验收。

独立 Reviewer 不是固定门禁。只有公共接口、权限安全、数据库迁移、高扇出基础组件、大量删除替换或多 Agent 集成等高风险证据出现时才调用。Reviewer 只读检查提交后的同一内容版本，并返回：

```json
{"reviewer":"原生工具返回的独立Agent标识", "verdict":"pass", "digest":"submit返回的摘要", "summary":"实际审查范围、证据与结论"}
```

`verdict` 只接受 `pass`/`fail`，身份不得等于实施 Agent 或 Root owner。Root 核实真实工具身份，不能自行编造身份冒充独立审查。未调用 Reviewer 时，`accept` 只要求计划中的检查通过、无未完成事项、范围无越界且内容摘要一致；已经记录 Review 时则必须通过。只有实质修复使证据失效时，才重新 `submit` 并复查受影响部分。

## 外部上下文与跨会话接力

外部上下文保存在同一项目的 `.workflow/state.sqlite3`，属于可重建工作集，不是聊天归档。上下文 JSON 必须精炼且不超过 64 KiB：

```json
{
  "objective": "仍需完成的最终目标",
  "current_phase": "当前阶段",
  "completed": ["已经验证的事项"],
  "decisions": ["重要决定及理由"],
  "assumptions": ["仍有效的假设"],
  "blockers": [],
  "next_actions": ["下一条具体动作"],
  "references": ["测试、Review、事件或用户授权的引用"],
  "updated_files": ["src/example.py"]
}
```

先运行 `context` 获取当前 `revision`；保存时携带该 revision，避免用陈旧状态覆盖新进度：

```powershell
& $wfPython $wfScript --root $wfRoot context
& $wfPython $wfScript --root $wfRoot pressure
& $wfPython $wfScript --root $wfRoot checkpoint --owner $rootTaskId --context context.json --expected-revision 12
```

`pressure` 返回 `normal`、`soft` 或 `hard`，以及 `proxy_ratio`、`metric=workflow-events-not-model-token-percentage`、`signal_only=true` 和以下结构化能力说明：

```json
{
  "capability": {
    "model_token_telemetry": false,
    "pressure_source": "workflow-events-since-checkpoint",
    "successor_creation": "host-only",
    "controller_behavior": "signal-only"
  }
}
```

这是 checkpoint 后的事件量代理；平台没有向 Skill/脚本提供精确的剩余 token 百分比，任何级别都不能表述成真实上下文余量。soft 时立即 checkpoint；hard 时准备 handoff。若 `auto_create_successor=true`，Root 必须先核对保存的用户授权引用，再调用 Codex `create_thread` 创建同项目后继任务，将目标、checkpoint、账本路径、MCP 项目/代次和下一步写入新任务提示。该布尔值只是建议信号，不会让脚本自行调用平台；平台未返回真实任务 ID 时不得 prepare。

换会话使用两阶段交接。`successor` 必须使用真实的后继任务标识，token 只传给该后继任务：

```powershell
& $wfPython $wfScript --root $wfRoot handoff-prepare --owner $rootTaskId --successor $nextTaskId --context context.json --expected-revision 13
& $wfPython $wfScript --root $wfRoot handoff-accept --successor $nextTaskId --handoff-token $handoffToken
```

后继会话在 accept 前读取返回的 resume 包，核对项目根目录、Git 状态、活动 Agent、任务占用和相关源码。accept 是原子接管确认；旧会话仅在看到成功回执后停止调度。若后继会话未能接管，旧会话使用 `handoff-cancel --owner ... --handoff-token ...` 取消，不能按超时推定成功。该机制不复制未落盘的思考；控制器本身不创建会话，只有在用户已明确授权自动接力时，Root 才可依据建议调用平台创建任务。

checkpoint 的 `coordinator` 防止不同会话互相覆盖上下文，但现有任务 claim token 仍是任务操作凭据；旧会话交接后必须停止使用已有 token。控制器不能撤销已经发出的原生工具调用，因此接管前仍需核对执行者状态。

## 失败与恢复

```powershell
& $wfPython $wfScript --root $wfRoot suspend T001 --token $claimToken --status blocked --reason '真实阻塞原因'
& $wfPython $wfScript --root $wfRoot retry T001 --token $claimToken --stopped-reference '核对执行者停止的实际工具回执引用'
& $wfPython $wfScript --root $wfRoot approve T002 --reference '用户批准具体操作的会话引用'
```

`suspend` 支持 `blocked`/`failed`，保留占用，不因时间流逝自动释放。`retry` 只在 Root 已确认原执行者停止后调用，清除令牌、回到 pending，下次领取产生新令牌；旧令牌失效。每任务最多三次执行尝试，达到上限先重新评估原因和范围。创建 Agent 后未绑定就中断时，也要先核对是否存在已创建执行者，不直接重派。

事件不会在重试时删除，但这是普通本地 SQLite 文件，不具备身份认证、防篡改或自动备份能力。Root 只在当前执行期间调度；后续会话需重新读取 Skill 和状态，不承诺后台常驻。
